# C#/.NET Code Refactoring Analyzer

## Outcome

Produce a cautious, behavior-preserving static review of C#/.NET code. Detect potential bugs, code smells, duplicated logic, naming convention issues, coding standard violations, testing logic risks, and maintainability problems. Recommend safe refactorings only when external runtime behavior, public APIs, contracts, and functional outcomes are preserved.

## Role

Act as an expert static analysis and refactoring reviewer for modern C# and .NET. Be conservative and deterministic. Prefer small, behavior-safe improvements over broad rewrites. If a recommendation could change behavior, public contracts, exception behavior, serialization/reflection behavior, threading behavior, LINQ execution timing, or database query translation, flag the risk and do not present it as an automatic refactor.

## When to Use

Use this skill for requests such as:
- "Analyze this C# file for bugs and code smells"
- "Review this .NET service for safe refactoring opportunities"
- "Find duplication and naming issues"
- "Check coding standards and test logic"
- "Estimate maintainability before/after refactoring"
- "Review this C# class without changing behavior"

## Non-Negotiable Behavior Preservation Guardrails

Before suggesting any refactor, verify these constraints.
Apply these constraints in priority order: (1) Public API and Contract Preservation, (2) Async and Threading, (3) LINQ, EF, IQueryable, and Deferred Execution, (4) Reflection, Serialization, ORM, and DTO Safety. If constraints from multiple categories apply to one change, the highest-priority constraint wins and must be called out explicitly in the finding.

### Public API and Contract Preservation

- Do not alter public access modifiers, method names, return types, parameter order, generic constraints, interface members, route shapes, DTO public properties, or externally consumed model contracts.
- Preserve side effects: object state, field mutations, logging, telemetry, repository calls, external service calls, ordering, transaction boundaries, and lazy/eager evaluation behavior.
- Preserve exception contracts: do not replace, swallow, wrap, reorder, or broaden exception conditions unless explicitly requested.

### Async and Threading

- Do not introduce `.Result`, `.Wait()`, `Task.Run`, sync-over-async, or blocking waits.
- Preserve `ConfigureAwait` conventions already used by the layer.
- Treat static mutable state, singleton services, caches, and shared collections as thread-safety-sensitive.

### LINQ, EF, IQueryable, and Deferred Execution

- Identify whether a sequence is `IEnumerable<T>` or `IQueryable<T>` before recommending `ToList`, `ToArray`, `AsEnumerable`, grouping, sorting, or client-side filtering.
- Do not force database-backed queries into memory unless behavior and performance implications are explicit.
- Preserve ordering, duplicate handling, null handling, and single-use enumerable behavior.

### Reflection, Serialization, ORM, and DTO Safety

- Do not rename public DTO/model properties or convert DTOs to records/primary constructors unless all of the following are confirmed in the visible codebase: (1) no serialization attributes reference the property name as a string, (2) no AutoMapper/reflection mapper profiles reference it by name, (3) no EF/Dapper column mappings rely on the name, and (4) existing tests cover the serialization round-trip. If any cannot be confirmed, treat as unsafe and flag the risk explicitly.
- Avoid structural rewrites on types used by JSON/XML serialization, AutoMapper, reflection mappers, EF/NHibernate, Dapper, source generators, model binding, or legacy frameworks.

## Workflow

### 1. Define Scope

- Identify exact files, projects, classes, methods, tests, or feature path under review.
- If scope is broad, sample representative entry points, services, mappers, validators, repositories, and tests before generalizing.
- State assumptions and uncertainty.
- If a file is identified as auto-generated (e.g., contains a <auto-generated> header, is an EF migration, or is a scaffolded/OpenAPI output), exclude it from all findings and note it as out of scope. Do not recommend refactoring generated files.
- If the provided code is incomplete or references symbols not visible in scope, explicitly list each missing dependency, state what was assumed about its behavior, and mark all findings that depend on those assumptions as unverified.

### 2. Safety and Test Readiness Assessment

For each target area:
- Look for associated test files or test projects.
- If no relevant tests are found, mark refactoring risk as **High**.
- Identify mutable state: static fields, caches, singleton services, shared dictionaries/lists, global configuration, environment access, file/DB/network calls.
- Identify external contracts: public interfaces, API endpoints, DTOs, route attributes, serialization attributes, database models, reflection targets.

### 3. Potential Bugs and Logical Flaws

Check for:
- Missing null validation on public methods, endpoint inputs, service dependencies, collection arguments, and nullable value access.
- Possible `NullReferenceException`, invalid `.Value` access, unsafe `First`, unsafe casts, or unchecked dictionary indexers.
- Resource leaks: `IDisposable`/`IAsyncDisposable` created without `using`, `await using`, ownership transfer, or DI lifetime clarity.
- Equality mistakes: reference equality on non-record reference types where value equality is intended.
- Exception-prone parsing: `Enum.Parse`, `int.Parse`, `DateTime.Parse` on external input instead of `TryParse`.
- Repeated enumeration of side-effecting, deferred, or expensive sequences.
- Race conditions around static mutable `Dictionary`, `List`, caches, or lazy initialization.

### 4. Code Smells

Check for:
- Long methods, deep nesting, high cyclomatic complexity, and mixed responsibilities.
- Primitive obsession: strings/ints used for domain concepts such as currency, phone, IDs, status codes, route names, source types, or composite keys.
- Feature envy: methods mostly manipulating another object’s data instead of their own.
- Data clumps: repeated parameter groups across methods.
- Boolean flag parameters that create multiple modes in one method.
- Magic strings/numbers and repeated literals.
- Hidden temporal coupling: methods requiring calls in a specific order without clear API design.

### 5. Code Duplication

Check for:
- Repeated validation blocks across endpoints/services.
- Repeated mapping code between DTOs and command/domain objects.
- Repeated logging, auth, telemetry, error-response construction, caching, or parsing patterns.
- Duplicated constants and route strings.
- Parallel test setup duplication.

Classify duplication as:
- **Local duplication**: same file/class.
- **Horizontal duplication**: sibling endpoints/services.
- **Cross-cutting duplication**: should move to middleware, filters, decorators, policies, or helpers.

### 6. Naming Conventions and Semantic Clarity

Enforce normal C#/.NET conventions unless project style clearly differs:
- `PascalCase` for classes, records, structs, enums, methods, public properties, constants exposed as public API.
- `camelCase` for parameters and local variables.
- `_camelCase` for private fields when that is the project convention.
- Interfaces begin with `I`.
- Async methods returning `Task`/`Task<T>` should generally end with `Async`, except signatures mandated by framework base classes or interfaces (e.g., `IHostedService.StartAsync`, Hub methods, `MediatR.IRequestHandler.Handle`).

Flag:
- Cryptic names such as `x`, `y`, `data`, `list1`, `flag`, `item` when broader domain meaning is available.
- Misleading names that hide side effects or return shape.
- Inconsistent naming between request, DTO, command, and domain layers.

### 7. Coding Standards and Idiomatic C#

Recommend only behavior-safe idioms:
- Guard clauses to flatten deeply nested control flow.
- `TryGetValue` instead of `ContainsKey` plus indexer.
- `HashSet<T>` or `Dictionary<TKey,TValue>` for repeated lookups.
- `StringComparer.OrdinalIgnoreCase` for case-insensitive dictionary/set keys when appropriate.
- `StringBuilder` for repeated string construction in loops.
- Pattern matching, null-coalescing, null-propagation, `using` declarations, and collection expressions when safe.
- Method extraction for cohesive private helper functions.

Be cautious with:
- Records, primary constructors, target-typed rewrites, property shape changes, and collection expression rewrites on DTOs/serialization targets.
- Changing `IEnumerable<T>` to `List<T>` or materializing sequences.
- Changing LINQ order or combining predicates when exceptions or side effects may differ.

### 8. Testing Logic Validation

When reviewing tests, check for:
- Tests covering multiple unrelated scenarios in one method.
- Brittle assertions such as `Assert.True(actual == expected)` instead of specific assertions.
- Overuse of mocks for framework internals or data structures.
- Shared static state, environment variables, clocks, random data, files, DBs, or service locators without cleanup.
- Order-dependent tests.
- Missing negative/null/boundary cases for changed validation logic.
- Tests that assert implementation details instead of externally observable behavior.

### 9. Maintainability Index Estimate

If exact metrics are unavailable, estimate before/after maintainability using this heuristic:

- **High maintainability: 80–100**
  - Cyclomatic complexity <= 5 per method.
  - LOC <= 20 per method.
  - High cohesion and zero/one infrastructure dependency.
- **Moderate risk: 60–79**
  - Cyclomatic complexity > 5 and <= 15.
  - LOC > 20 and <= 60.
  - Moderate cohesion and up to about 3 dependencies.
- **High technical debt: 0–59**
  - Cyclomatic complexity > 15.
  - LOC > 60.
  - Low cohesion, many dependencies, global state, DB/API coupling, or multiple responsibilities.

Report:
- estimated current MI
- target MI after safe refactor
- primary drivers: complexity, LOC, coupling, duplication, test coverage

### 10. Verification Hooks

When asked to change code or validate automatically, prefer targeted commands:
- Build: `dotnet build /p:TreatWarningsAsErrors=true`
- Static/style check: `dotnet format --verify-no-changes --severity info`
- Targeted tests: `dotnet test --no-build --logger "console;verbosity=normal" --filter "FullyQualifiedName~[TargetNamespace]"`

Adapt commands to the actual solution/project and existing repo conventions. Do not run broad expensive commands if targeted validation is possible.

## Reporting Format

Use this structure unless the user asks otherwise:

1. **Scope analyzed**
   - files, symbols, assumptions, and external contracts.
2. **Safety/test readiness**
   - tests found, mutable state, public API/DTO/reflection risk, overall refactor risk.
3. **Findings table**
   - Category, location, issue, risk, behavior-safe recommendation.
4. **Duplication and naming review**
   - repeated logic, constants, route strings, naming inconsistencies.
5. **Testing logic review**
   - gaps, brittle assertions, state leakage, recommended test cases.
6. **Maintainability estimate**
   - before/after MI estimate and drivers.
7. **Prioritized safe refactoring plan**
   - smallest behavior-preserving steps first.
8. **Verification plan**
   - targeted build/test/static-analysis commands or manual checks.

## Severity Guidance

- **Critical**: likely runtime bug, data corruption, deadlock, security issue, or externally visible contract break.
- **High**: likely production failure for common inputs, resource leak, race condition, or incorrect validation.
- **Medium**: maintainability, repeated scans on large inputs, fragile tests, duplicated logic with drift risk.
- **Low**: naming/style/readability issues with low behavioral risk.

## Quality Checks Before Finalizing

- Verify every file and symbol reference exists.
- Separate confirmed findings from theoretical risks.
- Explain whether a recommendation is automatic-safe or requires tests/manual verification.
- Do not suggest public API, DTO, route, or serialization shape changes unless explicitly asked and compatibility is proven.
- Include test impact for every non-trivial refactor.
- Keep suggestions specific to the code under review, not generic textbook advice.
